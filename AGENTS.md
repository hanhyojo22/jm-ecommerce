# Codex project instructions

## Project goal

Build a local-first MVP for a multi-vendor online marketplace. Registered sellers can create a shop and list their own products. Buyers can browse products and place orders. Platform admins can review sellers, products, and orders. VPS deployment is a later, separate phase.

## Before coding

- Inspect the repository, README, configuration, and existing tests before changing code.
- Follow the project's actual language, framework, and conventions. Do not introduce TypeScript or a new framework merely as a preference.
- If this file is copied into a different project, update the project goal and commands before relying on it.
- Make a short implementation plan for changes that span several files. Identify unclear requirements and state reasonable assumptions.

## MVP scope

- Roles: buyer, seller, and platform admin. Enforce permissions on the server, not only in the UI.
- Seller flow: register or sign in, create a shop, manage only their own products, and view only their own orders.
- Buyer flow: browse and search products, view product details, manage a cart, place an order, and view their own order history.
- Admin flow: view sellers and shops, see what categories and products each seller offers, moderate listings, and review orders.
- Use a simple local development database and seed data. Keep database configuration portable for a later VPS deployment.
- Keep payments, shipping integrations, subscriptions, and production deployment outside the MVP unless explicitly requested. A clearly labeled manual or test checkout is acceptable for local development.

## Engineering rules

- Prefer a small, understandable monolith for the MVP. Keep UI, business logic, and data access responsibilities clear.
- Make every seller-owned query and mutation tenant-scoped. Never trust a seller ID supplied by the client as proof of ownership.
- Validate input on the server. Use parameterized queries or the framework's safe database APIs.
- Store passwords with the framework's established secure hashing method. Keep secrets in environment variables and provide an `.env.example` without real credentials.
- Represent money in integer minor units or an exact decimal type; never use floating-point arithmetic for order totals.
- Treat order prices as a snapshot at checkout so later product edits do not change historical orders.
- Add database migrations for schema changes. Do not edit applied migrations in place.
- Keep changes focused. Preserve existing behavior and data unless the task explicitly requires a change.
- Avoid unnecessary dependencies and speculative abstractions.

## Workflow and verification

1. Read the relevant files and trace the existing flow.
2. Implement the smallest complete change, including authorization and error states.
3. Add or update tests for business rules, tenant isolation, and order calculations when those behaviors change.
4. Run the relevant formatter, linter, tests, and build commands available in the repository. Do not claim a check passed unless it ran.
5. Report what changed, what was verified, and any remaining limitation.

- The requested flow works from the UI through the server and database.
- A seller cannot read or change another seller's private records.
- Buyers see only their own account and order information.

- Relevant checks pass, or the exact blocker is recorded.
- Setup steps and new environment variables are documented.

1. Use words for auto-stemmed AND logic: `rate limit` matches both "rate" AND "limit".
2. Use `"quoted phrases"` for exact position matching: `"infinite scroll"` requires adjacent words in order.

4. Use multiple queries for OR logic: `queries=["authentication", "middleware"]`.
