# OCR and document data extraction for Philippine senior citizen, PWD, and PhilID cards

Scope note: evidence gathered November 2026. Sources are labelled where they are vendor marketing rather than independent measurement. No real ID numbers or personal data are reproduced here.

## How does an ID OCR pipeline work end to end?

### Takeaway
A production ID pipeline is not "OCR then regex". It is a staged system — capture-quality gating, document detection/classification, text detection and recognition, then key-information extraction (KIE) from templates, MRZ, or QR — followed by field validation and a confidence/review decision. The stages that decide real-world accuracy are the first (image quality) and the last (validation), not the recogniser in the middle.

### Cited Findings
- **Capture quality gating.** Google's ML Kit states that each character should ideally be at least 16×16 pixels, that there is no accuracy benefit above 24×24 pixels, and that poor focus degrades recognition so the app should ask the user to recapture — [ML Kit, Android text recognition v2](https://developers.google.com/ml-kit/vision/text-recognition/v2/android).
- **Capture quality, vendor view.** Regula documents that camera resolution and focus are significant causes of incorrect extraction, and ships an image-quality assessment module for exactly this reason — [Regula, image quality assessment](https://docs.regulaforensics.com/develop/doc-reader-sdk/overview/image-quality/).
- **Capture quality, government view.** The PSA's PhilSys Check requires a camera of 720p or higher and at least 8 megapixels, with "visual effects and/or enhancements … disabled" and good lighting; it warns that lower-spec devices may fail QR scanning — [PhilSys Check](https://philsys.gov.ph/philsys-check).
- **Frame-by-frame gating.** BlinkID's core session returns, for every processed frame, a processing status (success, "awaiting-other-side", or a failure reason) plus a "result completeness" object explaining what data is still missing — [Microblink, how the SDK works](https://docs.microblink.com/blinkid/how-the-sdk-works).
- **Document detection and cropping.** Mindee's edge detector finds each document in a photo, returns its coordinates, and reads each separately; Klippa's API auto-crops uncropped uploads — [Mindee](https://www.mindee.com/); [Klippa ID Verification API](https://www.klippa.com/en/identity-verification/api).
- **Classification.** Scanbot 9.0.0 (June 2026) added ML-based document-type classification; BlinkID exposes a class filter to accept/reject document classes; Accura Scan's API instead requires the caller to pass `country_code` and `card_code`, i.e. the template is selected up front rather than inferred — [Microblink SDK comparison](https://microblink.com/resources/blog/best-id-scanning-sdk); [Accura OCR API](https://docs.accurascan.com/language/web-api/accura-ocr).
- **Text detection and recognition output structure.** ML Kit returns blocks → lines → elements (words) → symbols, each with bounding boxes, corner points, rotation, confidence score and recognised language — [ML Kit text recognition v2](https://developers.google.com/ml-kit/vision/text-recognition/v2).
- **Template matching.** Accura Scan describes a "template matching check" that validates the uploaded document matches the approved structure/layout before OCR is allowed to run — [Accura Scan Ooredoo case study](https://accurascan.com/blog-ooredoo-kuwait-automates-sim-registration-process-with-accura-scan).
- **MRZ parsing.** MRZ is a fixed-width, checksum-bearing format defined by ICAO Doc 9303 (TD1/TD2/TD3, MRV-A/B); Regula documents the formats and the check-digit rules — [Regula, MRTD types and MRZ formats](https://docs.regulaforensics.com/develop/doc-reader-sdk/overview/machine-readable-travel-documents/).
- **MRZ cross-check as validation.** Klippa validates by cross-checking the MRZ against the visual inspection zone and by verifying the MRZ checksum — [Klippa ID Verification API](https://www.klippa.com/en/identity-verification/api).
- **QR decoding.** The PhilID/ePhilID QR conforms to ISO/IEC 18004:2015, carries JSON that is *not encrypted*, and is integrity-checked by a digital signature inside the JSON; PSA publishes the public keys so relying parties can verify offline — [PSA advisory on PhilID verification](https://psa.gov.ph/content/advisory).
- **Confidence scoring.** Azure returns a confidence value per extracted field; Mindee returns a confidence score on every value plus bounding boxes; ML Kit returns a confidence score per element — [Azure ID document model](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/id-document?view=doc-intel-4.0.0); [Mindee platform](https://www.mindee.com/platform); [ML Kit](https://developers.google.com/ml-kit/vision/text-recognition/v2).
- **Quality analysis as a product feature.** Google's Enterprise Document OCR includes a "quality assessment of a document based on the readability of its content" — [Google Document AI processors list](https://cloud.google.com/document-ai/docs/processors-list).

### Inferences
- A workable ordering is: capture gate → detect/crop/perspective-correct → classify → OCR → extract by template/MRZ/QR → validate → score → auto-accept / review / reject. Vendors that skip the capture gate (plain server OCR of an uploaded photo) inherit blur, glare and crop failures that no downstream model repairs.
- Because confidence is emitted at different granularities (per character/word in OCR, per field in KIE), a usable system needs a per-field confidence, not a single document score. Field-level confidence is what lets you auto-accept `date_of_birth` while sending `address` to review.
- The cheapest accuracy win for a small team is not a better recogniser; it is refusing bad frames (glare, blur, crop, low resolution) and cross-checking independent sources (MRZ vs visual zone, QR signature vs printed text).

### Gaps
- No public source quantifies how much each capture defect (glare, hologram, laminate reflection, motion blur) costs in field accuracy for ID cards specifically; the 16×16 px and 8 MP figures are guidelines, not measured error rates.
- No source found describing a standard, vendor-neutral confidence calibration for ID KIE; confidence values are not comparable across vendors.

## How do the cloud/document-AI options compare?

### Takeaway
The hyperscalers sell cheap, excellent *general* OCR but almost no Philippine ID coverage. Azure's prebuilt ID model is the closest thing to a generic ID extractor ($10 per 1,000 pages), but its documented document list has no Philippine entry; AWS's AnalyzeID is explicitly US-only; Google has no ID-extraction parser for the Philippines at all. Only the specialist ID-SDK vendors (Microblink, Regula, Klippa, Accura, Scanbot) publish Philippine document classes — and they sell annual licences, not per-scan APIs.

### Cited Findings
- **Google Cloud Vision** charges $1.50 per 1,000 units for Text Detection and Document Text Detection, with the first 1,000 units free each month, falling to $0.60 above 5 million units; one unit is one feature on one image and each PDF page counts as an image — [Google Cloud Vision pricing](https://cloud.google.com/vision/pricing).
- **Cloud Vision returns no fields.** It returns characters, words, blocks and bounding boxes; it has no key-value, table or custom-document-type extraction at any price, so the extraction layer is yours to build — [DocuOCR, Cloud Vision pricing analysis](https://docuocr.com/google-cloud-vision-pricing).
- **Google Document AI — OCR.** Enterprise Document OCR is listed at about $1.50 per 1,000 pages, and it explicitly supports Filipino (`fil`) and Tagalog (`tl`) with handwriting, in `asia-southeast1` among other regions — [Google Document AI processors list](https://cloud.google.com/document-ai/docs/processors-list); [Nutrient OCR API comparison](https://www.nutrient.io/blog/ocr-api-comparison).
- **Google Document AI — ID proofing only.** Google's only identity processor is the "Identity Document Proofing Parser", which supports **US passports, passcards and driver's licenses only**, English only, max 2 pages, and is available only in `eu` and `us` regions. It returns fraud signals (`is_identity_document`, `suspicious_words`, `image_manipulation`, `online_duplicate`), not demographic fields — [Google Document AI processors list](https://cloud.google.com/document-ai/docs/processors-list).
- **Google Document AI — custom extraction.** The Custom Extractor costs about $30 per 1,000 pages; generative extraction is officially English-only and available in `us`, `eu`, `northamerica-northeast1` and `asia-southeast1` — [Google Document AI processors list](https://cloud.google.com/document-ai/docs/processors-list); [DocuOCR](https://docuocr.com/blog/google-cloud-vision-vs-document-ai).
- **AWS Textract AnalyzeID.** Priced at $0.025 per page for the first 100,000 pages and $0.01 per page after, with a free tier of 100 pages/month for three months for new accounts — [AWS Textract pricing](https://aws.amazon.com/textract/pricing).
- **AWS AnalyzeID coverage is US-only.** It reads "US passports and US driver's licenses (English)"; the surrounding Textract documentation describes the API as understanding "U.S. passports, driver's licenses, and other IDs" without publishing a wider country list — [Foxit Textract alternatives analysis](https://developer-api.foxit.com/developer-blogs/api-guides-tutorials/amazon-textract-alternatives/); [AWS Textract pricing](https://aws.amazon.com/textract/pricing).
- **Azure Document Intelligence pricing.** Read OCR is $1.50 per 1,000 pages; all prebuilt models — including `prebuilt-idDocument` — are $10 per 1,000 pages; custom extraction is $30 per 1,000; the F0 free tier covers 500 pages/month but processes only the first two pages of each request — [Azure pricing](https://azure.microsoft.com/en-us/pricing/details/document-intelligence/); [Azure ID document docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/id-document?view=doc-intel-4.0.0).
- **Azure ID model coverage.** Documented types are: worldwide passports/passcards; US DL, ID card, green card, SSN card, military ID; India DL/PAN/Aadhaar; Australia DL/photo card/Key-pass; and "Other — Driver License, Identification Card, Residency Permit". There is **no Philippine entry**, and the model is structured around MRZ-bearing documents — [Azure ID document model](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/id-document?view=doc-intel-4.0.0).
- **Azure ID output fields.** Documented fields are Country, DateOfBirth, DateOfExpiration, DocumentNumber, FirstName, LastName, Nationality, Sex, MachineReadableZone, DocumentType, Address and Region, each with a confidence value — [Azure ID document model](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/id-document?view=doc-intel-4.0.0).
- **Mindee International ID.** Markets "national ID cards from any country … no template per country, no rules to maintain", returning names, document number, dates, address and MRZ lines with a confidence score per field; a 14-day free trial is offered — [Mindee International ID OCR](https://www.mindee.com/product/international-id-ocr-api).
- **Mindee pricing.** Starter is about $44/month billed annually for 6,000 credits (≈$0.044/credit); 1 processed page = 1 credit, and 1 processed page with a confidence score = 1.5 credits; Enterprise requires 500,000+ credits/year — [Mindee pricing](https://www.mindee.com/pricing).
- **Klippa (now Doxis AI.dp).** Claims 500+ ID types across 150+ countries and "data extraction accuracy up to 99%", with MRZ/NFC support, MRZ-vs-visual-zone cross-checks and tamper detection; no public per-scan price is published — [Klippa global coverage](https://www.klippa.com/en/identity-verification/global-coverage); [Klippa identity document OCR](https://www.klippa.com/en/ocr/identity-documents/).
- **Veryfi.** Bills per document (up to 15 pages), with published rates around $0.08 per receipt and $0.16 per invoice and a $500/month minimum on its Starter plan; its published strengths are financial documents, and no Philippine ID template coverage was found — [ReceiptOCR Veryfi pricing summary](https://receiptocr.ai/blog/veryfi-pricing); [Veryfi pricing](https://www.veryfi.com/pricing).
- **Microblink BlinkID — Philippine coverage.** The supported-document list includes, for the Philippines: Alien ID (ACR I-Card), Driver's License, eID, Health Insurance Card (PhilHealth), Identity Card (PhilSys ID / PhilID), Multipurpose ID (UMID), MySSS Card, Postal ID, Professional ID (PRC), Social Security Card (SSS), Tax ID (TIN), Voter ID, Work Permit (AEP); a Police ID was added in the November 2026 release — [BlinkID supported documents](https://docs.microblink.com/blinkid/supported-documents); [BlinkID November 2026 release notes](https://docs.microblink.com/blinkid/release-notes/november-2026).
- **Microblink — vendor claims.** BlinkID claims "over 95% data extraction accuracy", 2,500+ documents in 140+ countries, scanning under 3 seconds and a 98%+ first-time pass rate, and cites first place in the DHS Document Validation Rally 2025. These are vendor claims, not independently verified here — [Microblink Flutter blog](https://microblink.com/resources/blog/flutter-document-scanner); [PassportOCR SDK comparison](https://passportocr.com/guides/best-id-scanning-sdk).
- **Microblink — commercial model.** Licensing is quote-based and key-bound to the app ID; a 30-day trial key is available — [Microblink SDK comparison](https://microblink.com/resources/blog/best-id-scanning-sdk).
- **Regula.** Sells a Document Reader SDK with authenticity/security-feature checks, MRZ and NFC, licensed per device UID (a `devices.dat` file bound to device identifiers) — [Regula licensing models](https://docs.regulaforensics.com/develop/doc-reader-sdk/overview/licensing). Pricing is quote-based.
- **Scanbot.** A capture-only SDK: MRZ scanning, AAMVA PDF417 parsing, and front-side field extraction for a mostly European document set; it does not verify documents. Published starting price is a flat **$2,500/year per app or domain with unlimited scans**, 7-day trial — [Microblink SDK comparison](https://microblink.com/resources/blog/best-id-scanning-sdk).
- **Accura Scan.** Claims 3,500+ (elsewhere 12,000+) ID documents, 150+ languages, 195+ countries and 99.95–99.99% accuracy; sells yearly licences with unlimited usage, a 30-day trial, Android/iOS/server SDKs, a web API, and an on-premise Docker OCR image — [Accura OCR pricing](https://accurascan.com/ocr-pricing); [Accura Scan home](https://accurascan.com/); [Accura OCR docs](https://docs.accurascan.com/language/web-api/accura-ocr).
- **IDScan.** Publishes per-verification pricing for its DIVE service: about $0.50 per verification at 400/month falling to $0.40 at 2,000/month, plus $175 per Windows device for ID parsing — [Microblink SDK comparison](https://microblink.com/resources/blog/best-id-scanning-sdk).
- **Data residency.** Google Document AI's OCR and Custom Extractor are available in `asia-southeast1` (Singapore); its ID Proofing parser is not (EU/US only) — [Google Document AI processors list](https://cloud.google.com/document-ai/docs/processors-list). No vendor documentation found confirms where Azure's `prebuilt-idDocument` or AWS AnalyzeID physically process Philippine customer data.
- **Latency reference points.** BlinkID claims under 3 seconds per scan; Accura claims 5–10 seconds for a full KYC flow; Mindee says "in seconds" — [Microblink](https://microblink.com/resources/blog/flutter-document-scanner); [Accura Scan](https://accurascan.com/); [Mindee](https://www.mindee.com/product/international-id-ocr-api). The Philippine government's NIDAS authentication API is specified at 1–5 seconds per transaction — [RegTech.com NIDAS summary](https://www.regtech.com/news/philippines-national-id-everify-relying-party-onboarding).

### Inferences
- For a Philippine-only marketplace, the cloud "ID document" endpoints are mostly unusable as *extractors*: AWS AnalyzeID is US-only, Google has no ID extractor, and Azure's generic model is MRZ-shaped and undocumented for PhilID/OSCA/PWD. Using them would mean falling back to plain OCR plus your own parser — which is the "build" option with extra steps.
- The specialist SDKs' value is not OCR quality per se but the document library: someone has already modelled PhilID, UMID, PhilHealth, Postal, PRC, SSS, TIN and Voter IDs. That library is the moat and the reason pricing is annual and quote-based rather than per scan.
- At low volume the economics invert: a cloud API at $0.01/scan is trivial, but a $2,500+/year SDK is not. At 1,000 verifications/month, $10–$25/month of Azure/AWS is cheaper than any annual SDK licence; at 50,000/month the SDK's unlimited-scan licence wins.

### Gaps
- No public list price for BlinkID, Regula, Klippa or Accura; all are "contact sales". Any build-vs-buy comparison must obtain quotes.
- No documentation confirms whether Azure `prebuilt-idDocument` actually recognizes PhilID, UMID, OSCA or PWD cards; the "Other" row is not a coverage guarantee.
- No published latency benchmarks for BlinkID/Regula/Accura on mid-range Android hardware; all figures are vendor claims.
- Data residency for Azure/AWS ID models in Southeast Asia was not verified from primary docs in this pass.

## How do the open-source / self-hosted options compare?

### Takeaway
Open-source OCR is good at *reading text* and poor at *reading ID cards*. The best independent ID-specific benchmark found (DocXPand-25k) puts Tesseract 5.3.3 at 54.5% field accuracy on identity documents, with fewer than half of MRZ fields read perfectly. PaddleOCR is materially stronger and fast enough on CPU, but it still returns text, not fields — the KIE layer, template set and validation are the real work.

### Cited Findings
- **Tesseract on ID cards — independent benchmark.** On DocXPand-25k (25,463 annotated fields across ID cards, residence permits and passports), Tesseract 5.3.3 achieved **54.5% field accuracy**, with 54.8% on numeric fields, 60.1% on alphabetic fields, 42.8% on alphanumeric fields, and **48.6% of MRZ fields read perfectly**; average CER was 50.6% overall and 2.52% on MRZ characters — [DocXPand-25k paper, arXiv 2407.20662](https://arxiv.org/pdf/2407.20662).
- **Tesseract on degraded cards.** An Indonesian e-KTP study measured 39.55% baseline OCR accuracy on 10 cards (150 attributes), rising to 64.97% after grayscale, denoising, CLAHE and thresholding — [IJSECS 2025](https://journal.lembagakita.com/ijsecs/article/download/5183/3620).
- **Tesseract on real-world KTP, larger sample.** A 78-image KTP evaluation reported **CER 69.82%, WER 80.20% and average field-level accuracy 30.18%**, with structured fields above 60% but free-text address/occupation much worse; the same pipeline scored ~96% character accuracy on two clean images, showing how strongly results depend on capture quality — [JEECS 2025](https://ejournal.ubhara.ac.id/index.php/jeecs/article/download/1595/577).
- **PaddleOCR accuracy.** PP-OCRv5 published recognition accuracy is 86.79% on printed English for `PP-OCRv5_server_rec` and 87.53% for `PP-OCRv5_mobile_rec`; handwriting is much weaker (58.06% and 49.44% on handwritten English respectively) — [PaddleOCR PP-OCRv5 docs](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv5/PP-OCRv5.en.md).
- **PaddleOCR accuracy — conflicting summary.** A third-party summary lists PP-OCRv5 English accuracy as 64.70% (server) and 66.00% (mobile), and 85.25% for the English-specific `en_PP-OCRv5_mobile_rec`; the spread reflects different evaluation sets, not a typo — [DocuOCR PaddleOCR analysis](https://docuocr.com/paddleocr).
- **PaddleOCR speed.** On an Intel Xeon Gold 6271C, PP-OCRv5 mobile averaged **1.75 s/image** (peak RAM ~2.2 GB), while PP-OCRv5 server averaged 4.34 s/image; on a Tesla V100 the same models averaged 0.62 s and 0.74 s — [PaddleOCR PP-OCRv5 docs](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv5/PP-OCRv5.en.md).
- **PaddleOCR mobile/edge speed.** A C++ ncnn implementation measured PP-OCRv5 mobile at **92 ms on a simple image and 1,063 ms on a complex image** on a 2-vCPU Xeon; PP-OCRv6 tiny at 67 ms / 420 ms, with peak memory 62–157 MB — [PaddleOCR-ncnn-CPP benchmarks](https://github.com/Avafly/PaddleOCR-ncnn-CPP).
- **PP-OCRv6 CPU benchmark.** Independent CPU testing reports PP-OCRv6 tiny at **0.26 s/page**, small at 0.90 s/page, medium at 5.25 s/page, versus PP-OCRv5 server at 5.25 s/page; PP-OCRv6 medium read 123 of 124 items exactly versus 117 for PP-OCRv5 server — [paddleocr.dev benchmarks](https://paddleocr.dev/benchmarks).
- **Tesseract vs PaddleOCR, independent.** OmniDocBench normalized edit distance (lower is better): English text 0.071 for PaddleOCR 2.9.1 vs 0.096 for Tesseract 5.5; Chinese 0.055 vs 0.551; rotated 90° 0.015 vs 0.117 — [DocuOCR, citing OmniDocBench](https://docuocr.com/paddleocr).
- **EasyOCR.** In a video-OCR benchmark, EasyOCR scored 49.30% average accuracy (CER 0.5070), versus 76.22% for GPT-4o and 76.13% for Gemini-1.5 Pro; RapidOCR scored 56.98% — [VideoDB OCR benchmark, arXiv 2502.06445](https://arxiv.org/html/2502.06445).
- **Donut fine-tuned.** Donut reaches 94.40% F1 on SROIE receipt KIE after fine-tuning, competitive with LayoutLM-family models — [OCR vs Donut comparative study](https://sergeisolovev.com/papers/ocr-vs-donut.pdf).
- **Donut without fine-tuning.** The same study finds Donut "achieves near-zero F1" without fine-tuning, and that even 2 epochs on 38% of the data yields a 37.5× improvement — [OCR vs Donut comparative study](https://sergeisolovev.com/papers/ocr-vs-donut.pdf).
- **Donut on ID cards.** A Vietnamese ID-card project trained Donut on synthetic cards, needed a custom decoder vocabulary for Vietnamese diacritics, and reported ~4 seconds inference including an alignment model, tested on a very small real dataset — [NashTech Donut ID card writeup](https://blog.nashtechglobal.com/id-card-extraction-with-donut-and-how-to-support-for-specific-languages).
- **Donut field accuracy.** A receipt project reports 61.90% full-match accuracy and 94.66% average string similarity across company/date/address/total fields after fine-tuning — [ocr-layoutlmv3-vs-ocr-free-donut](https://github.com/PneumaGo/ocr-layoutlmv3-vs-ocr-free-donut).
- **LayoutLMv3 and OCR error cascade.** LayoutLMv3 scores 96.6 F1 with ground-truth OCR but **80.5 F1 with a real OCR engine** — a ~16-point drop caused purely by OCR errors — [See then Tell, arXiv 2409.19573](https://arxiv.org/html/2409.19573v2).
- **OCRBench v2 (LMM OCR capability).** Most large multimodal models score below 50/100; on text recognition specifically, Qwen2.5-VL-7B scores 73.0, InternVL3-14B 71.1, GPT-4o 74.1, Gemini-1.5-Pro 64.1, versus 38.1 for CRNN and 62.4 for ABINet — [OCRBench v2, arXiv 2501.00321](https://arxiv.org/html/2501.00321).
- **OCRBench v2 failure modes.** InternVL3-14B scores 79.1% on high-frequency text but **46.7% on low-frequency text** (dot-matrix, occluded, CAPTCHA-like); LMMs can roughly locate an answer but struggle to output the exact region — [OCRBench v2](https://arxiv.org/html/2501.00321).
- **Benchmark limits.** OCRBench/OCRBench v2 measure scene text, documents, charts and receipts — not government ID cards. DocXPand-25k is the only ID-specific public benchmark found here, and it covers synthetic/template-driven European-style documents — [OCRBench v2](https://arxiv.org/html/2501.00321); [DocXPand-25k](https://arxiv.org/pdf/2407.20662).

### Inferences
- For a small team, "fine-tune a VLM on ID cards" is a multi-month data project, not a sprint: you need labelled real cards, and the closest public evidence (Donut on receipts) shows zero-shot performance near zero and heavy dependence on fine-tuning.
- A realistic self-hosted stack is: PaddleOCR (or a managed OCR) for text + a hand-built template/ROI extractor per ID type + regex/date/checksum validation. That is exactly the layer commercial ID SDKs already ship.
- Throughput on commodity CPU is fine for a pharmacy marketplace: ~1–2 s per card on 4 vCPU with PP-OCRv5 mobile, ~0.3 s with PP-OCRv6 tiny. Latency is not the constraint; accuracy and template maintenance are.
- Expect Tesseract alone to be unusable for straight-through ID extraction; it is a fallback or a second opinion, not a primary engine.

### Gaps
- No independent accuracy figures were found for docTR, TrOCR, Florence-2 or Qwen-VL specifically on ID cards; OCRBench scores are a proxy at best.
- No public Philippine-ID test set or benchmark exists (see final section), so all open-source accuracy figures above are transferred from Indonesian, Vietnamese, European or receipt domains.
- No source quantifies the annotation cost (images × fields × minutes) for fine-tuning an ID KIE model, which is the dominant cost of the build option.

## On-device vs server-side OCR: what are the trade-offs?

### Takeaway
On-device OCR is free, offline, private and fast enough for capture gating and prefill, but it gives you text, not verified fields. Server-side gives you better models and central control but ships sensitive government-ID images off the device. For Philippine IDs the strongest architecture is a hybrid: on-device capture/quality/QR, server-side validation and storage of the minimum necessary data.

### Cited Findings
- **ML Kit Text Recognition v2.** Recognises Latin, Chinese, Devanagari, Japanese and Korean; returns blocks/lines/elements/symbols with boxes, rotation and confidence; runs on-device and offline — [ML Kit text recognition v2](https://developers.google.com/ml-kit/vision/text-recognition/v2).
- **ML Kit size cost.** iOS adds about **38 MB per script SDK**; Android bundled adds about **4 MB per script per architecture**, or about **260 KB unbundled** (model downloaded via Play Services) — [ML Kit iOS](https://developers.google.com/ml-kit/vision/text-recognition/v2/ios); [ML Kit Android (Chinese docs, same table)](https://developers.google.com/ml-kit/vision/text-recognition/v2/android?hl=zh-cn).
- **ML Kit language coverage.** Filipino (`fil`) and Cebuano (`ceb`, experimental) appear in the evaluated/experimental language lists — [ML Kit supported languages](https://developers.google.com/ml-kit/vision/text-recognition/v2/languages).
- **ML Kit accuracy claims.** A third-party summary attributes 96% accuracy on Latin text and 10–30 ms per frame to ML Kit, and 95% / 10–40 ms to Apple Vision — these are secondary claims, not Google/Apple published figures — [IT Sectr comparison](https://itsectr.com/en/knowledge/on-device-ml/text-recognition).
- **Apple Vision.** Ships with iOS/macOS (no app-size cost), supports 26 languages in the current request API, and requires iOS 13+ — [textdet.com comparison](https://textdet.com/guides/text-detection-android-ios).
- **PP-OCR on-device.** PP-OCR models can run on mobile via ONNX Runtime/ncnn at roughly 6.4 MB of models plus runtime, with PP-OCRv6 tiny around 67–260 ms per image — [textdet.com](https://textdet.com/guides/text-detection-android-ios); [PaddleOCR-ncnn-CPP](https://github.com/Avafly/PaddleOCR-ncnn-CPP).
- **BlinkID is on-device.** Capture, detection and extraction happen on the phone; the Flutter plugin exposes `performScan` and `performDirectApiScan`, but **React Native and Flutter do not expose the frame-by-frame core session** — [BlinkID how it works](https://docs.microblink.com/blinkid/how-the-sdk-works); [blinkid-flutter](https://github.com/BlinkID/blinkid-flutter).
- **Scanbot is offline.** Requires no internet connection and runs fully on-device; Flutter SDK supports Android/iOS only (not web/desktop) — [Scanbot Flutter docs](http://docs.scanbot.io/flutter/data-capture-modules/introduction).
- **Accura can run offline.** The mobile app/SDK works without internet, and a Docker image is available for on-premise server OCR — [Accura Scan download page](https://accurascan.com/download); [Accura OCR docs](https://docs.accurascan.com/language/web-api/accura-ocr).
- **Privacy exposure is real and legally material.** Under the Data Privacy Act, government-issued identifiers and biometric data are **sensitive personal information**, whose processing is prohibited unless a specific lawful basis (usually explicit consent) applies — [RA 10173 text](https://privacy.gov.ph/Data-Privacy-Act/); [NPC Advisory Opinion 2025-015](https://privacy.gov.ph/wp-content/uploads/2026/01/NPC-Advisory-Opinion-No.-2025-015_Redact_redacted.pdf).
- **PhilSys QR data is sensitive PI.** The NPC advises that the PhilSys QR code and any data derived from it in KYC must be treated as sensitive personal information, subject to stricter requirements, and that a processor must be bound by a written outsourcing agreement covering security, confidentiality, retention and data-subject rights — [NPC Advisory Opinion 2025-015](https://privacy.gov.ph/wp-content/uploads/2026/01/NPC-Advisory-Opinion-No.-2025-015_Redact_redacted.pdf).
- **Retention limits.** The DPA IRR requires personal data to be retained only as long as necessary for the declared purpose, and disposed of securely — [DPA IRR](https://privacy.gov.ph/wp-content/uploads/2017/03/IRR-of-the-DPA.pdf).
- **Government cloud order carve-out.** EO 119 (2026) states that routine collection or storage by private entities of copies of government-issued identification documents for legitimate business purposes is **not** treated as government data under that order — [EO 119](https://lawphil.net/executive/execord/eo2026/pdf/eo_119_2026.pdf).

### Inferences
- On-device is the right place for the *capture gate*: it stops bad frames before upload, saves bandwidth, and avoids sending rejected images to a third party at all. It is the wrong place to make the final discount decision, because the device can be tampered with.
- Sending an ID image to a US or EU OCR API is a cross-border transfer of sensitive personal information; it needs an explicit lawful basis, a processor agreement and a retention story. On-device extraction plus upload of only the *fields* (not the image) is materially easier to defend.
- A practical split: ML Kit (free) or BlinkID (paid) on-device for capture + prefill; your Laravel server for validation, duplicate checks, audit logging and the discount decision; the raw image stored encrypted only if you have a documented retention period.

### Gaps
- No measured comparison of ML Kit vs BlinkID vs Regula extraction accuracy on Philippine IDs was found.
- No source documents Philippine-specific rules on whether storing an ID image (versus extracted fields) requires additional NPC registration or a DPIA; this needs legal review.
- No power/thermal/battery data for on-device OCR on low-end Android phones common in the Philippine market.

## What breaks OCR on Philippine IDs?

### Takeaway
Philippine IDs break OCR for structural reasons, not just image-quality reasons. PhilID has no MRZ (it has a signed QR), OSCA and PWD cards are LGU-issued with no single national template, many carry no expiry, and the fields most likely to be wrong (long addresses, suffixed/accented names) are exactly the ones the discount decision depends on.

### Cited Findings
- **PhilID has a QR, not an MRZ.** The PhilID/ePhilID QR encodes JSON (name, sex, date and place of birth, PCN, date of issuance, best fingerprint; plus a portrait for ePhilID) and is signed by PSA; PSA publishes public keys so relying parties can verify offline — [PSA advisory](https://psa.gov.ph/content/advisory); [PhilSys Check](https://philsys.gov.ph/philsys-check).
- **PhilID QR verification is fragile in practice.** PSA specifies a camera of 8 MP and 720p, enhancements disabled and good lighting; reproduced ePhilID copies "may have lower quality and can affect the QR code image and its scanning" — [PhilSys Check](https://philsys.gov.ph/philsys-check); [PIA ePhilID explainer](https://pia.gov.ph/regions/everything-you-need-to-know-about-the-ephilid/).
- **PhilID formats vary.** The card exists as a physical PVC PhilID, a paper ePhilID, and a Digital National ID in the eGovPH app; all are valid subject to authentication — [PhilSys FAQ](https://philsys.gov.ph/faq-frequently-asked-questions).
- **Digital National ID is a screenshot-able artifact.** The NCSC says the digital National Senior Citizens ID can be screenshotted and shown, and requires internet only to access/update — [NCSC digital NSCID](https://www.ncsc.gov.ph/ncsid). There is no documented cryptographic check for the digital NSCID comparable to PhilSys Check.
- **OSCA IDs have no national template.** RA 9994 requires OSCA to issue national individual identification cards free of charge, valid nationwide; issuance is by the city/municipal OSCA (or barangay captain), and LGU citizen's charters list different requirements and formats — [RA 9994 via Supreme Court E-Library](https://elibrary.judiciary.gov.ph/thebookshelf/showdocs/10/77065); [Muntinlupa OSCA charter](https://muntinlupacity.gov.ph/wp-content/uploads/2026/06/OSCA-CC-2026-LIVE-1.pdf); [Naga OSCA charter](https://www2.naga.gov.ph/wp-content/uploads/2026/06/x-CC-CMO-OSCA-1-5.pdf).
- **OSCA IDs have no statutory expiry.** RA 9994 sets no expiry; guidance says to check the card and the issuing OSCA — [Sulat.ph OSCA guide](https://sulat.ph/government-documents/how-to/senior-citizen-id-requirements).
- **PWD IDs are LGU-issued but nationally specified.** NCDA AO 001-2021 prescribes the standard PWD ID card, valid for **five years**, initial issuance free, with a control number and the guardian's name on the card — [NCDA AO 001-2021](https://ncda.gov.ph/disability-laws/administrative-orders/ncda-administrative-order-no-001-series-of-2021); [PhilForms PWD guide](https://philforms.com/guide/pwd-id-and-discount).
- **PWD validity is changing.** NCDA AO 001-2026 introduces a Unified PWD ID with **lifetime validity for permanent disabilities**, five-year revalidation for non-apparent disabilities, and a transition period — [Manila Bulletin, 8 Nov 2026](https://mb.com.ph/2026/11/08/unified-digital-pwd-id-where-to-register-and-what-to-prepare); [The Philippines Web PWD guide](https://thephilippinesweb.com/how-to-apply-for-a-pwd-id-in-the-philippines-2026).
- **Handwriting is the weak spot of every engine.** PP-OCRv5 server recognition is 58.06% on handwritten English versus 86.79% on printed English; mobile is 49.44% vs 87.53% — [PaddleOCR PP-OCRv5 docs](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv5/PP-OCRv5.en.md).
- **Alphanumeric and free-text fields are the weakest.** DocXPand-25k: 42.8% accuracy on alphanumeric fields and 60.1% on alphabetic fields, versus 54.8% numeric; addresses and unusual fonts were called out as the hardest fields — [DocXPand-25k](https://arxiv.org/pdf/2407.20662).
- **Low-frequency text defeats LMMs.** OCRBench v2 shows a 32-point gap between high-frequency and low-frequency text for InternVL3-14B (79.1% vs 46.7%) — [OCRBench v2](https://arxiv.org/html/2501.00321).
- **Unknown templates are handled by library size or by generic extraction.** Mindee claims template-free extraction "regardless of design, language or alphabet"; Klippa claims 500+ ID types; Accura claims 3,500–12,000 documents; BlinkID lists explicit Philippine classes — [Mindee](https://www.mindee.com/product/international-id-ocr-api); [Klippa](https://www.klippa.com/en/identity-verification/global-coverage); [Accura](https://accurascan.com/); [BlinkID](https://docs.microblink.com/blinkid/supported-documents).
- **VLM hallucination is measurable.** LMMs struggle with precise spatial grounding and low-frequency text; Donut without fine-tuning achieves near-zero F1; a fine-tuned Donut still produced only 61.9% exact-match field accuracy on receipts — [OCRBench v2](https://arxiv.org/html/2501.00321); [OCR vs Donut](https://sergeisolovev.com/papers/ocr-vs-donut.pdf); [Donut receipt project](https://github.com/PneumaGo/ocr-layoutlmv3-vs-ocr-free-donut).

### Inferences
- PhilID is the *easiest* Philippine ID to handle correctly, but not via OCR: read the QR, verify the signature with PSA's public key (or call PhilSys Check/eVerify), and use OCR only to cross-check the printed name/DOB against the QR payload. Treating PhilID as an OCR problem throws away the one cryptographically verifiable signal on the card.
- OSCA and PWD cards are the *hardest*: no national template, LGU printing, lamination/holograms, handwritten signatures, and often no expiry. Any vendor claiming "any country, no templates" should be tested specifically on 20–30 real OSCA/PWD cards from different LGUs before being believed.
- Names with ñ, accents and suffixes (Jr., III) are a normalization problem more than an OCR problem: even a correct read needs canonicalization before matching to an account. No Philippine-specific accuracy data exists, so this must be tested, not assumed.
- Hallucination detection needs provenance: require a bounding box for every extracted field, reject fields whose text cannot be located in the OCR output, and cross-check independent fields (DOB vs age vs ID number pattern vs QR/MRZ). A VLM that returns a plausible-looking address with no supporting pixels should be treated as a failure, not a success.

### Gaps
- No public study measures OCR accuracy on PhilID, OSCA, PWD, 4Ps, barangay or UMID cards. This is the single biggest evidence gap in this research.
- No source documents failure rates caused by lamination, holograms, or laminate glare on Philippine cards specifically.
- No source addresses OCR behaviour on Filipino names with ñ/accents or on very long multi-line Philippine addresses; the nearest evidence is generic alphanumeric/address field accuracy.
- 4Ps (Pantawid Pamilyang Pilipino Program) IDs, barangay IDs and solo-parent IDs were not covered by any vendor's published Philippine document list that I found.
- No documentation was found on whether the digital NSCID or Digital National ID exposes a verifiable signature that third parties can check offline.

## Which fields must be extracted to make the discount decision, and which validations are realistic?

### Takeaway
The discount decision needs surprisingly few fields: ID type, ID number, full name, date of birth, expiry (if any), and — for audit and fraud — address and photo. The hard part is that the legal eligibility test is *age ≥ 60 for seniors* and *a valid PWD ID for PWDs*, while the identifiers themselves have no national checksum; only PhilID offers cryptographic verification.

### Cited Findings
- **Senior eligibility and accepted IDs.** RA 9994 defines a senior citizen as a resident citizen at least 60 years old and accepts, as proof: an OSCA-issued ID, a Philippine passport, or other documents establishing citizenship and age (driver's licence, voter's ID, SSS/GSIS ID, PRC card, postal ID) — [RA 9994 text](https://elibrary.judiciary.gov.ph/thebookshelf/showdocs/10/77065); [FDA Advisory 2024-0429](https://www.fda.gov.ph/fda-advisory-no-2024-0429-clarification-on-the-requirements-for-senior-citizens-to-avail-20-discount-on-medicines).
- **The OSCA ID must be honoured nationwide**, including for medicine discounts — [RA 9994](https://elibrary.judiciary.gov.ph/thebookshelf/showdocs/10/77065); [FDA Advisory 2024-0429](https://www.fda.gov.ph/fda-advisory-no-2024-0429-clarification-on-the-requirements-for-senior-citizens-to-avail-20-discount-on-medicines).
- **BIR requires the ID number on the invoice.** Revenue Regulations No. 7-2010 requires that a claim for the 20% senior discount be supported by the availing senior citizen's ID card number — [NCMB Resolution citing RR 7-2010](https://elibrary.judiciary.gov.ph/thebookshelf/showdocs/10/77065).
- **PWD eligibility and accepted proof.** RA 7277 as amended by RA 10754 grants 20% discount and VAT exemption on medicines and other items; proof is the PWD ID issued by the LGU through the PDAO/CSWDO — [NCDA AO 001-2021](https://ncda.gov.ph/disability-laws/administrative-orders/ncda-administrative-order-no-001-series-of-2021); [DOH AO 2017-0008](https://ncda.gov.ph/disability-laws/administrative-orders/doh-ao-2017-0008-implementing-guidelines-of-republic-act-10754-otherwise-known-as-an-act-expanding-the-benefits-and-privileges-of-persons-with-disability-for).
- **A person cannot take both discounts.** The PWD IRR states that a person who is also a senior citizen uses either the PWD ID or the senior ID, not both; on a promo, the store discount or the 20%, whichever is higher — [PhilForms PWD guide](https://philforms.com/guide/pwd-id-and-discount).
- **PWD purchase booklet.** Discounted medicine purchases require the PWD ID *and* the purchase booklet, which records the purchase — [Legazpi PDAO charter](https://legazpi.gov.ph/wp-content/uploads/2026/06/CMO-PDAO-2026.pdf).
- **PWD ID contents.** The standard card carries name, address, date of birth, disability type, control number, guardian name and validity — [NCDA AO 001-2021](https://ncda.gov.ph/disability-laws/administrative-orders/ncda-administrative-order-no-001-series-of-2021); [PhilForms](https://philforms.com/guide/pwd-id-and-discount).
- **PhilSys Card Number.** The PCN is a 16-digit number printed in four groups (e.g. `1234-5678-9012-3456`); the QR payload carries it alongside name, sex, DOB, place of birth, date of issuance and best fingerprint — [PhilSys Check](https://verify.philsys.gov.ph/).
- **PhilID authentication tiers.** Tier 0 is QR-vs-card matching; Tier I basic online authentication returns match/no-match plus registered full name; Tier II eKYC returns verified demographics and the registration portrait and can prefill forms — [RegTech.com NIDAS summary](https://www.regtech.com/news/philippines-national-id-everify-relying-party-onboarding); [PSA press release PDF](https://rsso06.psa.gov.ph/sites/default/files/article/2025-PR21-%20PSA%20RSSO%206%20Enjoins%20Government%20and%20Private%20Organizations%20to%20Integrate%20with%20the%20National%20ID%20Authentication%20System.pdf).
- **NIDAS is free and fast, but gated.** Published service levels: 99.5% monthly availability, 1,000 authentication transactions/minute per system, 1–5 second responses; private-sector relying parties pay nothing "at present". Onboarding requires a Letter of Intent, business-process map, 30-day temporary API key, VAPT certificate and a subscription contract signed by both DPOs; review is 7–10 working days and full go-live is weeks to months — [RegTech.com](https://www.regtech.com/news/philippines-national-id-everify-relying-party-onboarding).
- **Vendors cannot be relying parties.** Technology providers and software vendors cannot register as relying parties on their own; they may only act as solution partners, with accountability staying with the relying party — [RegTech.com](https://www.regtech.com/news/philippines-national-id-everify-relying-party-onboarding).
- **No checksum for LGU IDs.** No source found documents a check digit, national format or public validation algorithm for OSCA or PWD ID numbers; they are LGU-assigned control numbers — [NCDA AO 001-2021](https://ncda.gov.ph/disability-laws/administrative-orders/ncda-administrative-order-no-001-series-of-2021).

### Inferences
- Minimum viable field set: `id_type`, `id_number`, `full_name`, `date_of_birth`, `expiry` (nullable), `address`, `photo`. For PWD add `disability_type` and `booklet_number` if medicines are discounted. For PhilID add `pcn` and a stored verification result/token.
- Realistic automated checks, strongest to weakest: (1) PhilID QR signature / NIDAS Tier I–II result; (2) age ≥ 60 computed from DOB; (3) expiry not in the past, treating OSCA as no-expiry and PWD as 5-year or lifetime depending on issuance date; (4) fuzzy name match against the account with suffix/accent normalization; (5) duplicate-ID detection across accounts (same ID number used twice); (6) ID-number format sanity only where a format is known (PCN 16 digits), not for OSCA/PWD.
- Because BIR requires the ID number on the invoice, the ID number must be captured accurately even when the rest of the card is unreadable — a strong argument for a review step rather than silent auto-correction.
- A "verified" flag should record *how* verification happened (QR signature, NIDAS tier, manual review), not just a boolean; otherwise you cannot defend the discount in an audit.

### Gaps
- No authoritative published format or checksum for OSCA or PWD ID numbers was found; LGUs appear to assign control numbers independently.
- No source states whether PhilSys Check / eVerify can be used by a pharmacy marketplace without becoming a relying party; the rules say vendors cannot be RPs, so the marketplace itself would need to onboard.
- No guidance found on how long a marketplace may retain a copy of an OSCA/PWD card image; the DPA requires necessity-based retention but gives no sector-specific period.

## Independent accuracy evidence vs vendor marketing

### Takeaway
There is credible independent evidence that classical OCR struggles on ID cards and that VLMs are unreliable on rare text and precise layout — but almost none of it is Philippine-specific. Every vendor number in this space (95%, 99%, 99.95%) is self-reported, and no NIST-style independent evaluation of ID-document OCR exists.

### Cited Findings
- **Independent, ID-specific.** DocXPand-25k is a public benchmark of 25,463 annotated fields from identity documents, with per-field-type and per-template accuracy; Tesseract 5.3.3 scores 54.5% field accuracy and 48.6% perfect MRZ fields — [DocXPand-25k, arXiv 2407.20662](https://arxiv.org/pdf/2407.20662).
- **Independent, OCR-general.** OCRBench v2 (NeurIPS 2025 Datasets & Benchmarks) provides 10,000 human-verified QA pairs across 31 scenarios and a 1,500-image private test set; most LMMs score below 50/100 — [OCRBench v2, NeurIPS 2025](https://proceedings.neurips.cc//paper_files/paper/2025/hash/8c2e6bb15be1894b8fb4e0f9bcad1739-Abstract-Datasets_and_Benchmarks_Track.html).
- **Independent, document-parsing.** OmniDocBench normalized edit distances show PaddleOCR 2.9.1 beating Tesseract 5.5 on English (0.071 vs 0.096) and dramatically on Chinese (0.055 vs 0.551) — [DocuOCR, citing OmniDocBench](https://docuocr.com/paddleocr).
- **Independent, receipts/KIE.** Donut fine-tuned reaches 94.40% F1 on SROIE; BROS-Large reaches 96.62%; LayoutLMv3 drops from 96.6 to 80.5 F1 when real OCR replaces ground-truth text — [OCR vs Donut study](https://sergeisolovev.com/papers/ocr-vs-donut.pdf); [See then Tell](https://arxiv.org/html/2409.19573v2).
- **Vendor claim — Microblink.** "Over 95% data extraction accuracy", 2,500+ documents, 140+ countries, under 3 seconds, 98%+ first-time pass, DHS Document Validation Rally 2025 first place — [Microblink](https://microblink.com/resources/blog/flutter-document-scanner); [PassportOCR](https://passportocr.com/guides/best-id-scanning-sdk). No independent replication found.
- **Vendor claim — Klippa.** "Data extraction accuracy up to 99%" — [Klippa](https://www.klippa.com/en/ocr/identity-documents/). Methodology and test set not published.
- **Vendor claim — Accura Scan.** "99.95% accuracy" on the pricing page and "99.99% accuracy" on the product page — [Accura pricing](https://accurascan.com/ocr-pricing); [Accura passport/ID OCR](https://accurascan.com/passport-and-id-ocr). The two pages disagree, which is itself a caution.
- **Vendor claim — Scanbot.** No accuracy figure published; the vendor positions itself as capture-only and explicitly does not verify documents — [Microblink comparison](https://microblink.com/resources/blog/best-id-scanning-sdk).
- **Vendor claim — Azure/AWS/Google.** These publish model coverage and confidence outputs but no field-level accuracy figures for ID documents; there is no published recall/precision per field — [Azure ID model](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/id-document?view=doc-intel-4.0.0); [Google processors list](https://cloud.google.com/document-ai/docs/processors-list); [AWS Textract](https://aws.amazon.com/textract/pricing).
- **No NIST OCR evaluation.** No NIST evaluation of ID-document OCR or KIE was found; NIST's identity-related evaluations (FRVT) measure face recognition, not document text extraction. This is an absence of evidence, not evidence of absence.

### Inferences
- Treat all vendor accuracy numbers as upper bounds measured on curated, in-domain images. The honest planning assumption for a self-built pipeline on real Philippine phone photos is well below any vendor headline: the independent ID benchmark's 54.5% field accuracy for Tesseract and the 80.5 F1 for LayoutLMv3-with-real-OCR are better anchors than 95–99%.
- Because no Philippine benchmark exists, any vendor shortlist must be decided by a local bake-off: 30–50 real cards per type, across LGUs, lighting conditions and devices, scored per field (not per document).

### Synthesis: what this implies for build vs buy
- **PhilID:** do not buy OCR to verify it. Read the QR and verify the PSA signature (free), or onboard to NIDAS/eVerify (free, 1–5 s, but weeks-to-months of compliance work including VAPT and a DPO-signed contract). OCR is only for prefill and cross-check. [PhilSys Check](https://philsys.gov.ph/philsys-check); [RegTech NIDAS](https://www.regtech.com/news/philippines-national-id-everify-relying-party-onboarding)
- **OSCA/PWD:** there is no national registry API and no standard template, so "verification" is really assisted data entry plus human review. Buy only if a vendor can demonstrate named Philippine coverage and acceptable per-field accuracy on your own cards; Microblink is the only vendor found that publishes OSCA-adjacent classes (PhilID, UMID, PhilHealth, Postal, PRC, SSS, TIN, Voter, AEP), and even it does not list an OSCA or PWD card by name. [BlinkID supported documents](https://docs.microblink.com/blinkid/supported-documents)
- **Cheapest defensible build:** ML Kit on-device capture gate + field prefill; server-side PaddleOCR/Tesseract fallback; QR verification for PhilID; strict validation (age, expiry, duplicate ID, name/DOB match); manual review queue for low-confidence or LGU-issued cards; store fields, not images, unless a retention policy justifies otherwise.
- **When to buy:** if manual review volume exceeds roughly a few hundred cards a month, or if the business needs liability transfer and a vendor SLA, an annual ID-SDK licence becomes cheaper than engineering time — but only after a local bake-off, because no vendor publishes Philippine accuracy.

### Gaps
- No independent, published accuracy evaluation of any commercial ID SDK on Philippine IDs exists; every claim above is either vendor marketing or transferred from non-Philippine datasets.
- No public data on the cost or turnaround of a local bake-off (how many cards, how many annotators, how many hours).
- No evidence on how the 2026 Unified PWD ID transition affects existing cards' machine-readable layout, since the rollout is in progress.
